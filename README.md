# Examinus (working name)

Quizzes and exams for colleges and universities: live quizzes like Wayground, plus timed, scheduled exams with essay grading.

## Decisions so far
- Audience: colleges and universities.
- Scale: up to 500 players in one live quiz, or 500 students taking one exam at the same time.
- Stack: Next.js + Tailwind (`apps/web/`); Effect 4 + PostgreSQL (Drizzle) API (`apps/rpc/`), called over typed Effect RPC defined in `packages/contract/`; code runner on Docker (`apps/runner/`). Live updates run over an Effect RPC stream on a WebSocket; Redis comes when there is more than one API server.
- Auth: [Better Auth](https://better-auth.com) in `apps/rpc/` (email/password, optional Google), stored in PostgreSQL through Drizzle. The web app signs in through RPC and sets the session cookies the API returns; it forwards `/api/auth/*` (the Google callback) to the API.
- Roles: admin, teacher and student, each with its own area (`/admin`, `/teacher`, `/student`). Permissions per role live in `packages/contract/src/permissions.ts`; the API checks them in its RPC handlers, Better Auth's admin plugin enforces account management, and the web app checks them with `requirePermission` for pages and mock data.
- Hosting: web on Vercel; the API needs a host that keeps WebSocket connections open (Fly.io / Railway / Render).
- Name: the product is **Examinus** (everything people see). Code, packages (`@examora/*`), the database, cookies and storage keys, and the sandbox image keep the old name `examora` on purpose, so nothing needs migrating.
- Rate limiting: in the API (`apps/rpc/src/RateLimiter.ts`), because Better Auth's own limiter skips the server-side calls the RPC handlers make. Per-IP limits are wide (a whole class can share one campus IP); per-account and per-student ones are tight. Counts live in memory per API process and move to Redis with live quizzes. Per-IP limits trust `x-forwarded-for`, which Vercel sets; a self-hosted web app needs a proxy that overwrites it.

## Features
Everything below works today. Accounts, classes and rosters, attendance, quizzes, sessions, attempts and the question bank are stored in PostgreSQL through the API; the class record still runs on demo data in `apps/web/src/lib/data/` until it moves to the API.

### Teachers
- **Classes:** create a class and share its **class code**; students join with it. Edit or archive a class, make a new code, and remove students. Classes imported from Google Classroom show a link back to it.
- **Google Classroom:** "Connect Google Classroom" on Classes links the teacher's Google account with read-only Classroom access (it may be a different Google account from the one they sign in with). They then pick courses to import as classes, with their students; "Sync roster" on a linked class adds students who joined since (nobody is removed). Imported students have no student number or sex until they sign in with Google using the same email: their roster entry becomes theirs, and the join form asks for both. Email-and-password accounts never take over an imported entry, since their email isn't verified. Classroom has no schedule, so add one to each imported class for attendance.
- **Quizzes.** A quiz is reusable content: parts of questions, a test-paper layout and shuffling. A quiz with no session shows as Draft. A Subject dropdown decides the question types offered: General (multiple choice, blank, matching, enumeration, categorization, re-ordering, hotspot), English (+ true/false, essay; no hotspot), Mathematics (+ numeric; re-ordering), Science (all of General + true/false, numeric, essay), and Programming / IT (+ code, SQL query, categorization, re-ordering). "Show all question types" lifts the limit. Questions come from the editor, the question bank, or an Excel import.
- **Quiz editor.** "New quiz" (list, dashboard, class page, or `/teacher/assessments/new`) opens a dialog for the title, subject, description and the names of the parts before the editor opens; "Edit details" reopens it. The editor has a header (breadcrumb, totals, Saved / Unsaved changes), a details card, and one section per part with a labelled divider between parts and "Part settings" (instructions, shuffle, pool). Questions are compact cards that open to edit (Expand all / Collapse all) with a labelled field per setting. A **Cards | Table** switch shows the same quiz as a spreadsheet: a row per question grouped by part, inline editing from the keyboard (Enter or typing edits, Esc cancels, Tab and arrows move, Enter commits and moves down), multi-row bulk edits (points, game points, part), pasting columns from Excel or Sheets, row reorder and a side dialog with the full editor for complex questions. A collapsible contents panel (a drawer on small screens) jumps to the details, any part or any question and marks questions that need attention.
- **Markdown.** Prompts, choices, matching items, part instructions, the quiz description, students' essay answers and teacher feedback are markdown (bold, lists, tables, links, code), sanitised, with math written in LaTeX between `$…$` (or `$$…$$`). Every text box has a small toolbar and a Preview tab.
- **Question types.**
  - **Multiple choice:** one correct choice, or several (students tick every correct one), all-or-nothing or partial credit.
  - **Blank:** `fill` ("Identification / Fill in the blank") or `cloze` (a passage with many blanks). A `fill` question with no blanks in the prompt gives students one answer box and lists the accepted answers; with blanks inside the sentence they answer them in place. Blanks are written `{{answer|alternative}}` in the prompt, with an "Insert blank" button. Cloze blanks are typed, picked from a dropdown (options listed in the editor) or taken from a shared word bank with extra distractor words. Case sensitivity is per question.
  - **Matching:** left items, right items and extra distractors on the right; students drag each right item to its left item (keyboard and touch work too).
  - **Categorization:** 2 to 6 named categories (with an optional markdown description) and items with text and/or a picture; students drag each item into its category. An item with no category is a distractor that stays unsorted. Points are shared by the items (equal, or custom weights) with partial credit or all-or-nothing.
  - **Re-ordering:** 3 to 10 items you list in the correct order; students get them shuffled and drag them into order. One share of the points per correct position, or all-or-nothing.
  - **Hotspot:** an image with correct areas (rectangles or ellipses, optionally labelled); students click the image to place up to a set number of markers. One share of the points per area hit, or all-or-nothing (every area hit and no click outside). A tolerance widens every area a little.
  - **True/false, enumeration, numeric, essay (rubric rows with points), code and SQL.**
  - **Drawing:** students draw on a canvas (pen, highlighter, eraser, colours, thicknesses, text labels, undo/redo, pressure on tablets) and/or upload or take up to three photos of work done on paper; the teacher chooses which are allowed (and "Camera only" to refuse gallery picks), an optional background image to draw on, the canvas size, a rubric and the points. Graded by hand like an essay.
- **Parts.** You create, rename, reorder and delete parts, each with markdown instructions, and move questions between them (drag, or "Move to part" and up/down on a phone). A part can shuffle its questions or draw N of its M questions for each student (a pool). The printed paper uses your parts, with points per part ("Part II – Matching (10 pts)").
- **Points.** Every question has points (whole or half, default 1) and, per question, "all or nothing" or "partial credit". Points are shared equally among a question's blanks, pairs, items or tests, or you can set a weight for each. Essay rubric rows carry points that add up to the question's points. Each part and the whole quiz show live totals; bulk-set the points of a whole part or of one question type; every question in a pool needs the same points. A game-points setting (Standard, Double, None) is stored for the game mode and only shown under Advanced. Automatic scores are stored as a fraction and manual scores in points, so changing a question's points recalculates everyone's score.
- **Images.** Add pictures to prompts, part instructions and the quiz description ("Insert image", drag and drop, or paste a file), to multiple-choice options (shown as a grid) and to matching items. PNG, JPEG, WebP or GIF up to 5 MB; the browser shrinks them to 2000 px on the longest side and strips EXIF (location) before uploading. Alt text is required before a quiz can be saved and shows on the printed paper if an image can't load. Duplicating a quiz reuses the same images. Images sit in a private S3 bucket and are shown through short-lived signed URLs, so students can't see question images before the session opens.
- **Randomizing.** Shuffling is seeded from each attempt, so a student's paper is the same after a reload and the teacher sees exactly what they saw. The quiz can shuffle the order of parts, the questions within parts, multiple-choice choices, the matching right column and the cloze dropdowns and word bank; pools draw N questions per student. The answer key and scoring are never affected by the order.
- **Sessions.** "Start a session" on a quiz is one form in numbered sections: the type (Quiz, Exam, Mastery or Game, as cards), who (an **optional class** and its students, plus an optional room password), when (**Start now** or **Schedule for later**, optional close time, time limit, late-join cutoff), attempts (chips: 1, 2, 3, unlimited or custom) and when students see results (chips), the mode's own settings, and anti-cheating (toggle cards with a small drawing of each rule). Every session gets a **7-character join key**, made by the API (no 0/O, 1/I/L; unique among sessions that haven't ended). With a class, the roster is the class's members (`session_students` is the snapshot: filled from the class when the session is created, and when a student joins the class or enters the key as a member); a student who isn't a member can't join, and one who leaves the class or is removed comes off the sessions they haven't started. Without a class there is no roster: any student who has joined a class (so teachers can identify them) and enters the key joins, and "Count in the class record" is hidden. A session started now is running at once (a game opens its lobby); a scheduled one waits for its time (or Start), runs, and ends at its close time, when you press End, or when time is up; attempts still in progress are then submitted automatically by the API. Each session has its own results page: scores per student, by part and by question.
- **Mastery mode.** Choose "Mastery" when you start a session for self-paced practice: students get one question at a time and see right or wrong at once. A wrong answer goes back into their queue (after about three other questions, or at the end when fewer are left) until it is answered correctly or the **tries per question** (default 3, up to 10) run out. Optional **target score** (%) and **show the correct answer after the last wrong try**. Each question can have a markdown **explanation** (editor, under the question): students read it after a right answer, or after the last wrong try when the correct answer is shown, and it shows with the results. Essays, drawings and code without the runner are accepted once and wait for you to grade them. The queue is stored on the attempt, so a reload (or another browser) carries on exactly where the student was. The session results page has a mastery table (tries per question for each student), the live view shows questions mastered, and the student's results show tries per question and whether the target was reached. Anti-cheating defaults to blocking copy only; mastery mode doesn't use full screen.
- **Game mode.** Choose "Game" for a live game with points. **Teacher-paced** (like Kahoot): open the lobby from the presenter screen (`.../sessions/<session>/present`, built for a projector), students join with the 7-character join key (or the `/join?code=...` link), you start the game and move through each question: the question closes when its timer ends or everyone has answered, then the class sees how the answers split, the leaderboard (optional) and, at the end, the podium. You can remove a player in the lobby: the roster row stays, marked removed (`session_students.removed_at`), so they can't join again with the key ("You were removed from this session."). **Student-paced** (like Wayground): each student plays alone with a per-question timer while the presenter screen and the players show a live leaderboard. Settings: time per question (default 20 s), leaderboard after each question, streak bonus. **Points:** a correct answer earns `base × (1 − elapsed ÷ limit ÷ 2)` where the base is the question's game points (Standard 1000, Double 2000, None 0); partly correct answers earn that share and break the streak; each correct answer in a row after the first adds 100 (up to 500); a wrong answer earns 0. Game points are separate from the grading score: the normal score (and so the class record) ignores speed. Essay questions can't be used, code questions need a student-paced game, and drawing questions must be set to "No points": the presenter shows them as a class gallery with names hidden until you show them. The final standings are on the session results page and download as Excel; students see theirs when the game ends. The position of a teacher-paced game is saved in `quiz_sessions` (`game_phase`, `current_question_index`, `question_started_at`), so a restarted API resumes the same question with the time it had left.
- **Test paper layout** (a second tab in the editor): school header, paper size, part titles, footer and a live print preview; optional separate answer sheet.
- **Code questions:** Python, Java, C, C++, JavaScript and PHP (optionally with tables and Laravel's DB facade, query builder and Eloquent). Visible and hidden test cases, graded by `apps/runner/` in a sandbox.
- **SQL questions:** students query your tables; their rows are compared with your answer query (column names ignored), with an optional hidden-data check. Graded with sql.js (SQLite) on the server.
- **Review answers:** grade essays, re-score blank and enumeration answers (accept a near-miss), see code and SQL test results, and watch a **typing replay** of code answers.
  Drawing answers show the picture full size with zoom, a replay of the strokes, and tools to draw marks over it; students see the marks on their result.
- **Anti-cheating** (per session). Rules: full screen with a set number of chances before it submits itself, a log of tab and app switches (Alt+Tab included) with how long each lasted, one screen only (Chrome and Edge), separate switches for right-click, copy, paste (with an exception for code answers), printing and clearing the clipboard at the start, and a watermark with the student's name. Prevention: one question at a time with an optional time per question, a join key, a late-join cutoff, a room password, an IP allowlist (CIDR or plain addresses) and one device per attempt, all enforced by the API along with the timer. Detection: disconnects (heartbeat), time away, out of full screen and offline, device and network changes, a shared-device flag, answers that come too fast, pasted or robot-typed answers with a typing replay for code, SQL, essays and blanks, open dev tools and split screen. The Anti-cheating page gives each student an integrity level (low, medium, high) with the signals behind it, per-type counts and times, a timeline and minutes away, and runs checks after the session: matching rare wrong answers, essay text similarity, timing clusters, and a **similarity check** for code (renamed copies still match; common solutions are ignored). Shared devices or networks are only flagged, since campus Wi-Fi shares addresses. Students never see this.
- **Navigation & review** (session form, quiz and exam): **going back** is Free (any question), Back to marked only (forward, but students may return to a question while it is marked for review) or Forward only; the last two need one question at a time (a paper on one page is always free), and the API enforces them. **Questions a student may mark for review**: None allowed, 1, 3, 5, Unlimited or a custom number. Defaults: free and unlimited; exams start at back-to-marked-only and 5. The live view shows how many questions each student has marked, and the drawer and grading show which.
- **Live view** (`/teacher/assessments/<quiz>/sessions/<session>/live`): a table of every student (status, progress, current question, score so far, alerts, minutes away, integrity level) that updates as students answer, with each student's live answers, typing replay and event timeline in a drawer. Controls: start, pause and resume (every deadline moves by the time paused; nobody can save while paused), add time (everyone or one student), end, warn a student, lock and unlock a student (no saving until unlocked), force-submit, and allow back in (frees the attempt from its browser so a student whose computer crashed can continue on another). Every action is stored (`incidents` table) and shown in the timeline. Students see warnings, pauses, locks and new deadlines at once.
- **Exam mode** (the serious mode of a session).
  - **Locked settings:** full screen, tab and app logging, one screen, no right-click, copy, paste or printing, clipboard cleared at the start and the watermark are always on; you can only add stricter rules. Defaults: computers only, auto-submit after 3 chances, late join 15 minutes, one attempt, results released by hand.
  - **Device check and pledge:** phones and tablets are refused when "computers only" is on (checked by the API from the browser's headers). Students read the exam rules and accept an honor pledge (yours or the default) before the first question; the time they accepted is kept.
  - **Device switch approval:** an attempt that is open on another device, or that was away longer than the grace period (default 5 minutes), waits until you approve it. The live view opens each anti-cheating alert as a toast as it arrives, marks that student **Waiting for approval** and has an **Approve device switch** button (also in the student drawer). **Grant retake** in the drawer gives one named student another attempt, with a required reason.
  - **Answer history and grade changes:** every save of every answer is kept. Once results are released, changing a score asks for a reason in a dialog; the old and new score and the reason are kept. Each student's paper has a **paper version** code (like `A7K2-9QX`), shown on their result, in grading and on the report.
  - **Integrity report** per student (`…/sessions/<session>/report/<attempt>`): paper version, pledge time, device and IP, integrity level, counts and minutes per event type, a timeline of events and your actions, every answer version and every grade change. Print or **save as PDF**, or **Export Excel** (sheets Summary, Timeline, Events, Incidents, Answer history, Grade changes).
  - **Results export (Excel)** for every mode, on the session page and the grading page: name, student no., score, max, percent, integrity level, paper version and submission time, then the points of each part and each question.
- **Class record** per class, laid out like the school's Excel class record: categories with weights (ADW 60 + major exam 40), highest possible scores, RS and transmuted grades (TRANSMU table), and the course grade with P/F/FA/DR remarks. Sessions of the class are **added automatically** and score as students submit; removing one keeps it out. Excel download.
- **Attendance:** meetings are worked out from each class's schedule (the days in it, e.g. `MWF`, from the start of the semester to today; `meetingDates` in `packages/contract/src/attendance.ts`), so a new day's meeting appears on its own. Roll calls are stored in the `class_meetings` table; students see only their own. Roll call on a phone (present, late, absent, excused). 7 lates count as 1 absence, and 4 absences flag a drop (the teacher confirms DR). Absences and an Attendance item fill in the class record. Excel download per month with weekday names, plus a semester summary.
- **Collegiate grade sheet** (printable) and the **Summary report on class academic performance** (Reports).

### Students
- Dashboard of what's open, upcoming and done; Schedule; Scores; Classes, where they **join a class with its code** (the first time, also their student number and sex for the grade sheet) or leave one.
- **Join with a key** (dashboard, `/student/join` or `/join?code=...`): enter the 7-character key a teacher shows (any case; spaces and dashes are ignored, so `ABC-DEFG` works). It opens that session: if the session has a class you must be a member of it; a session without a class adds you to it (once you have joined any class) (the late-join cutoff still applies), and it then shows on your dashboard. A game takes you to its lobby (the late-join cutoff still applies), any other session to its usual page. In a game you answer on your own screen, see what each answer earned and your rank, and the final standings at the end.
- **Standing:** the grade so far in each subject, computed like the class record, with absences used out of the limit.
- Taking a quiz or exam: full screen, a timer the server enforces, answers saved to the server as you type (reloads and other devices pick up where you left off), and **Run** for code (Python and JavaScript in the browser, the rest on the code runner) on the sample tests only.
- **Question overview and review:** every question as a numbered tile (answered, not answered, marked for review, the one you're on, time ran out), in a side panel you can hide on wide screens and a sheet on phones, with "12 answered · 3 marked · 5 left". Click a tile to go there (scrolls on a one-page paper; one question at a time it opens the question when the session's going-back rule allows, and says why when it doesn't). **Mark for review** (flag) on each question is saved on the server. Before submitting, the review screen lists every question with your answer in a few words or "Not answered", marked ones first, with links back; you submit from there. A question you went back to while marked can be unmarked, but once you leave it unmarked you can't return; a question whose time ran out never reopens.
- **Drawing and photo answers:** draw on a canvas (strokes are saved as you go, and the picture is uploaded when you submit and every 30 seconds while you draw), or upload or take photos. Pasting an image is blocked when the session blocks paste.

### Everyone
- **Sign up** at `/register` with Google or any email and start right away. Students give their student number the first time they join a class. `/register` opens even when signed in (every "Start free" button leads there); signing up switches to the new account.
- **Rate limits:** 10 wrong passwords per account in 15 minutes, 200 failed sign-ins per IP in 10 minutes, 100 sign-ups per IP an hour, 300 Google sign-in starts per IP in 10 minutes, and 10 wrong class codes per student in 10 minutes. The page says how long to wait.
- **Auto sign-out** (`apps/web/src/components/session-watch.tsx`): after 30 minutes without activity in any tab, with a "Still there?" warning a minute before (not while taking an exam). Open pages also go to sign-in when the session ends elsewhere (expired, signed out in another tab, suspended). The login page says why and returns them to where they were.
- Landing page at `/`.

## Run the app
The API runs on [Bun](https://bun.sh) (1.3 or newer) and needs PostgreSQL and the variables in `apps/rpc/.env.example` (copy it to `apps/rpc/.env`); the web app needs `apps/web/.env.example` (copy it to `apps/web/.env.local`).
```bash
pnpm install
pnpm db:migrate     # apply migrations
pnpm db:seed        # test accounts admin@, teacher@, student@sic.edu.ph (password 12341234) plus demo accounts (examora-demo)
pnpm dev:rpc        # http://127.0.0.1:3001 (RPC at /rpc)
pnpm plan:set teacher@sic.edu.ph pro 2026-12-31   # change a teacher's plan (free, pro or ai); no date = no end
pnpm dev:web        # http://localhost:3000
```

Or with [devenv](https://devenv.sh), which provides Node 22, Bun, the pinned pnpm and PostgreSQL 17:
```bash
devenv shell        # then run the commands above; every variable except the Google pair is set
devenv up           # or start Postgres, migrate, seed, and start the API and the web app in one step
```

Postgres listens on `127.0.0.1:5434` with an `examora` database: `postgresql://127.0.0.1:5434/examora`.

devenv generates `BETTER_AUTH_SECRET` once per machine and stores it in `.devenv/state/auth-secret` (gitignored); delete that file to rotate it, which signs everyone out. Students and teachers can sign up at `/register` with any email, Gmail included, and are signed in right away. Admins create, edit, suspend and remove accounts at `/admin`. Both pages show a Google button; it works once `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set (redirect URI `<BETTER_AUTH_URL>/api/auth/callback/google`). "Sign up with Google" on `/register` creates the account with the chosen role; "Continue with Google" on `/login` only signs in to an existing account with the same email.

Accounts, quizzes, sessions, attempts, grades and the question bank live in Postgres behind the API, and survive restarts. Classes and their rosters are real too; the seed gives the test teacher the demo classes (codes `DBMS3AX`, `LOGIC1B`, `ELECT4A`), the demo quizzes and sessions for them, an account for each of the 24 demo students (password `examora-demo`), and roll calls for the demo classes from the start of the semester to yesterday. Class records still run on demo data in `apps/web/src/lib/data/mock.ts` and save in memory, so they're kept until the web server restarts; they move to the API later. `pnpm db:seed` loads the demo quizzes, sessions and submissions.

## Live sessions (WebSocket)
The browser can't send its login cookie to the API's host, so it never logs in to the WebSocket. The web server asks the API for a ticket (`live.ticket`, with the user's cookie): a signed (HMAC with `BETTER_AUTH_SECRET`), 60-second, single-use token for one teacher watching one session or one student following their own attempt. The browser opens `ws(s)://<API>/rpc/live` and sends the ticket with each request; every reconnect (with growing delays) gets a new ticket.
- `PUBLIC_API_URL` in `apps/web/.env.local` (optional): the API as the **browser** reaches it, e.g. `https://api.example.com` (the `ws://` / `wss://` URL is derived). The web server reads it at request time and sends it with each ticket, so changing it needs no rebuild. Without it, `API_URL` is used, which is enough for local development.
- Origin check: the API refuses a WebSocket upgrade from a browser whose `Origin` isn't the web app's: `LIVE_ALLOWED_ORIGINS` (comma separated, in `apps/rpc/.env`), by default the origin of `BETTER_AUTH_URL`. Requests without an Origin header aren't browsers and still need a valid ticket.
- The API must be reachable over WebSocket from browsers (a reverse proxy needs `Upgrade` headers and a long idle timeout).

## Run S3 storage (images and drawings)
Question images and students' drawings and photos are stored in an S3-compatible bucket (AWS S3, Cloudflare R2, Garage or MinIO). `devenv up` starts [Garage](https://garagehq.deuxfleurs.fr) with its S3 API on `127.0.0.1:3910` (data in `.devenv/state/garage`), creates an `examora` bucket with a development key and CORS rules, and sets the variables below. Without them the API still starts, but uploads fail with "Image storage isn't set up" and images are not shown.

| Variable | Meaning |
|---|---|
| `S3_BUCKET` | Bucket name, e.g. `examora` (private) |
| `S3_REGION` | e.g. `us-east-1` (Garage's default region) |
| `S3_ENDPOINT` | Empty for AWS S3; `http://127.0.0.1:3910` for devenv's Garage; the account endpoint for R2 |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Credentials with read, write and delete on the bucket |
| `S3_PUBLIC_ENDPOINT` | Optional: the address browsers use to reach the bucket when it differs from `S3_ENDPOINT` |

Browsers upload straight to the bucket (presigned POST, type and 5 MB limit enforced by S3), so the bucket's CORS rules must allow `POST` and `GET` from the web app's origin. devenv sets them on its Garage bucket; on AWS S3 or R2 add a CORS rule with the web origin, methods `POST` and `GET`, and any header. Without devenv, run any S3-compatible server yourself, create the bucket and a key with read and write on it, set CORS, and fill in the variables.
A daily job in the API deletes uploads that were never confirmed and images that no question, answer or bank entry refers to, once they are more than a day old.

## Google sign-in and Classroom (optional)
Both need a Google Cloud OAuth client; without one, the Google buttons are disabled.
1. In Google Cloud, create a project and enable the **Google Classroom API**.
2. Set up the OAuth consent screen. While it's in testing, add your accounts as test users. The Classroom scopes below are sensitive, so a public launch needs Google's verification.
3. Create an OAuth client (Web application) with the redirect URI `<BETTER_AUTH_URL>/api/auth/callback/google` (locally `http://localhost:3000/api/auth/callback/google`).
4. Put `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in `apps/rpc/.env` and restart the API.

Connecting Classroom asks for `classroom.courses.readonly`, `classroom.rosters.readonly` and `classroom.profile.emails` (`packages/contract/src/classroom.ts`), with offline access so syncing keeps working. `CLASSROOM_API_URL` and `GOOGLE_TOKEN_URL` override Google's endpoints for tests.

## Run the code runner (optional)
Code and SQL questions: the API grades SQL itself (sql.js in a worker thread); Python, Java, C, C++, JavaScript and PHP answers are run by `apps/runner/`, which needs Docker and which the API calls. (Students' Run button handles Python and JavaScript in the browser without it.)
```bash
pnpm runner:sandbox   # once: builds the examora-sandbox image
cp apps/runner/.env.example apps/runner/.env   # set RUNNER_SECRET
pnpm dev:runner       # http://127.0.0.1:4100
```
Set the same `RUNNER_SECRET` and `RUNNER_URL=http://127.0.0.1:4100` in `apps/rpc/.env`. Without the runner, code answers wait for the teacher to grade them.

## API
- `packages/contract`: RPC groups, schemas and errors shared by the web app and the API. Add a procedure here first.
- Quiz RPC groups (`packages/contract/src/quiz-rpc.ts`): `quiz.*` (quizzes, parts, questions, the question bank), `session.*` (create, update, start, end, release results, attempts, grade, class scores) and `attempt.*` (my sessions, the seeded paper, start, autosave, run sample tests, submit, integrity events, result, scores). Scoring and seeded shuffling are shared pure code in the contract (`scoring.ts`, `shuffle.ts`).
- Asset RPC group (`packages/contract/src/asset.ts`): `asset.createUpload` (presigned POST for one image, `question` images for teachers and `answer` images for students), `asset.confirm` (checks the file really is that image, records size and dimensions) and `asset.urls` (signed GET URLs only for assets the caller may see: their own, a quiz's images for its owner or for students on an open or ended session, students' answer images for the student and the session's teacher).
- Session lifecycle: a session is `scheduled` until its opening time (or until the teacher presses Start), `running`, then `ended` at its closing time or when the teacher ends it. A background job in the API runs every 30 seconds to open and end sessions and to submit attempts that ran past their time limit or the session's close (plus a 60-second grace). Answers are graded on submit: automatic scores in the API, code through the code runner (`RUNNER_URL`, `RUNNER_SECRET`), SQL through sql.js.
- Live sessions: `session.pause`, `resume`, `addTime`, `warn`, `setLocked`, `forceSubmit`, `allowBackIn` and `liveAttempt` (teacher actions), `live.ticket`, and the WebSocket group `LiveRpcs` (`packages/contract/src/live.ts`) at `/rpc/live` with the streams `live.teacher` (a snapshot, then changes) and `live.student` (pause, lock, deadline, warnings, "submitted"). The state is in Postgres (`quiz_sessions.paused_at`, `attempts.extra_ms` and `locked`, `incidents`), so a restarted API or a reconnecting browser shows the same thing; only the changes in flight live in memory (`Live.ts`, `LiveHub`), which is why one API server is enough for now.
- Mastery mode: `attempt.masteryState` (the saved queue and the question to answer now) and `attempt.masteryAnswer` (grades one try with the contract scoring and returns the feedback and the next state). The queue is `attempts.mastery_queue`, tries are `answers.tries` with every try in `answers.tries_log`, and the settings are `quiz_sessions.mastery`. The logic is in `apps/rpc/src/modes/mastery.ts`; `attempt.paper` sends no questions in this mode and `attempt.saveAnswer` is refused.
- Navigation and marks: `quiz_sessions.navigation` (`free`, `marked_only`, `forward_only`) and `max_marked` (0 off, null unlimited); `attempts.question_index` and `furthest_index`; `answers.marked_for_review` (a marked question without an answer has a row with a null value) and `answers.shown_ms` (time used on earlier visits of a question with a time limit). `attempt.goTo` moves one question at a time as `moveRefusal` in `packages/contract/src/review.ts` allows, `attempt.setMarked` refuses past `max_marked` (and, one question at a time, marking anything but the question you're on), and `attempt.saveAnswer` only takes the question the student is on. `attempt.paper` sends `review` (each question's answered/marked/closed state and answer summary) and `progress.furthest`.
- Game mode: `game.find` (join key to session; adds the student to a classless session), `game.join`, `game.answer`, `game.next` (student-paced), the teacher's `game.openLobby`, `start`, `advance`, `end`, `kick`, `standings` and `gallery`, and the WebSocket stream `live.game` (ticket target `game`) that sends each screen its whole `GameView` (presenter or player; a player never receives other players' answers or the answer before the question closes). The engine is `apps/rpc/src/modes/game.ts`: an in-memory room per game rebuilt from `quiz_sessions` (`game_phase`, `current_question_index`, `question_started_at`, game settings), `attempts` (`points`, `game_streak`) and `answers` (`game_points_earned`, `time_ms`) after a restart; a 500 ms ticker closes questions whose time is up. Points are `gameAnswerPoints` in `packages/contract/src/game.ts`.
- Exam mode: `quiz_sessions.exam` (computers only, honor pledge, device grace minutes), `attempts.pledge_accepted_at`, and the tables `answer_history` (every save) and `grade_changes` (score changes after release, with the reason). `session.create` and `session.update` refuse an exam with a locked anti-cheat setting off (`examLockedSettings` in `packages/contract/src/exam.ts`); `attempt.start` refuses phones and tablets (user agent and client hints) when computers only is on and refuses a new attempt without `pledgeAccepted`; an attempt on another device, or away longer than the grace period, gets the Conflict `deviceApprovalMessage` until the teacher calls `session.allowBackIn` (recorded as the incident `device_switch_allowed`). `session.grantRetake` (incident `retake_granted`, which adds one attempt for that student), `session.examRecord` (the integrity report's data) and the optional `reason` of `session.grade`. The server rules are in `apps/rpc/src/modes/exam.ts`.
- `apps/rpc/src`: Effect services (`Database`, `BetterAuth`, `Runner`, `Quizzes`, `LiveHub`, `Storage`, `Assets`), the auth middleware (`Session.ts`), RPC handlers (`handlers/`) and the server (`main.ts`). It runs on Node's built-in TypeScript support; no build step.
- `apps/web/src/lib/api/client.ts`: the RPC client. Server code calls `callApi((api) => api["admin.listUsers"](), forwardedHeaders(...))`.

Container: `apps/rpc/Dockerfile` (build from the repo root with `docker build -f apps/rpc/Dockerfile .`). It listens on `0.0.0.0:$PORT` (default 8080) and needs `DATABASE_URL`, `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` at runtime; it does not run migrations.

## Database
Schema: `apps/rpc/src/database/schemas/`. Migrations: `apps/rpc/src/database/migrations/`.
```bash
pnpm db:generate --name <change>   # after editing the schema; commit the generated SQL
pnpm db:migrate                    # apply pending migrations to DATABASE_URL
```

## CI
`.github/workflows/ci.yml` runs on pull requests and pushes to `main`: lint, typecheck, migration checks against a fresh PostgreSQL 17 (migrations apply, and the schema has no ungenerated changes), seed, an API start-up check, and the web build.

To migrate production on every push to `main`, add a `production` environment with a `DATABASE_URL` secret and set the repository variable `MIGRATE_ON_DEPLOY` to `true`.
