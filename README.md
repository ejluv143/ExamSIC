# Examinus (working name)

Quizzes and exams for colleges and universities: live quizzes like Wayground, plus timed, scheduled exams with essay grading.

## Decisions so far
- Audience: colleges and universities.
- Scale: up to 500 players in one live quiz, or 500 students taking one exam at the same time.
- Stack: Next.js App Router on [vinext](https://github.com/cloudflare/vinext) (Vite) + Tailwind (`apps/web/`); Effect 4 + PostgreSQL (Drizzle) API (`apps/rpc/`), called over typed Effect RPC defined in `packages/contract/` (the domain model it shares with the web app is in `packages/domain/`); code runner on Docker (`apps/runner/`). Live updates run over an Effect RPC stream on a WebSocket. Dragonfly (Redis protocol) holds the API's short-lived state and carries its event channels (see "Cache (Dragonfly)").
- Auth: [Better Auth](https://better-auth.com) in `apps/rpc/` (email/password, optional Google), stored in PostgreSQL through Drizzle. The web app signs in through RPC and sets the session cookies the API returns; it forwards `/api/auth/*` (the Google callback, the OAuth server below) to the API. Better Auth is also the OAuth 2.1 server AI assistants sign a teacher in through for the MCP server (`apps/mcp`, see its README): self-registered clients, the web app's `/login` and `/oauth/consent`, and JWT access tokens bound to `MCP_RESOURCE_URL` that `/rpc` accepts as `Authorization: Bearer`.
- Organizations and roles: an account has a platform role (`admin` runs the platform, `user`, `guest`) and belongs to one or more **organizations** (schools, departments; Better Auth's organization plugin), with one or more roles in each: `owner`, `admin`, `teacher`, `student`, or roles the organization defines itself (with `ORG_CUSTOM_ROLES=true`). The same account can teach in one organization and study in another. Every request runs in the session's **active organization**: classes, quizzes, question banks, sessions, images, rosters and AI keys belong to one organization, and a teacher in several switches between them from the sidebar (or `/organizations`). Each role has its own area (`/admin`, `/teacher` for owners, admins and teachers, `/student`). Permissions per role live in `packages/domain/src/permissions.ts`; the API checks them in its RPC handlers against the roles in the active organization, Better Auth's admin plugin enforces account management, and the web app checks them with `requirePermission` for pages.
- Hosting: the web build goes through Nitro (`nitro/vite`), which picks the platform output from the environment: on Vercel it writes `apps/web/.vercel/output` (set the Vercel project's Root Directory to `apps/web`); elsewhere `npm run build`, then `npm start` runs `apps/web/.output/server/index.mjs` on `$PORT`, default 3000. `API_URL` must be set at build time for the `/api/auth/*` rewrite and at runtime. The API needs a host that keeps WebSocket connections open (Fly.io / Railway / Render).
- Name: **Examinus** everywhere: the product, packages (`@examinus/*`), the database, cookies and storage keys, the S3 bucket and the sandbox image. Renamed from `examora`: existing deployments need the database and bucket renamed (or `DATABASE_URL`/`S3_BUCKET` pointed at the old ones), users are signed out and lose browser settings, saved AI keys must be entered again, and the runner needs `npm run runner:sandbox` again.
- Rate limiting: in the API (`apps/rpc/src/platform/RateLimiter.ts`), because Better Auth's own limiter skips the server-side calls the RPC handlers make. Per-IP limits are wide (a whole class can share one campus IP); per-account and per-student ones are tight. Counts are sliding windows in Dragonfly, shared by every API process (Better Auth's own limiter counts there too). Per-IP limits trust `x-forwarded-for`, so the web app needs a proxy in front of it that overwrites that header.

## Features
Everything below works today. Accounts, classes and rosters, attendance, class records, quizzes, sessions, attempts and the question bank are stored in PostgreSQL through the API.

### Teachers
- **Classes:** create a class and share its **class code**; students join with it. Edit or archive a class, make a new code, and remove students. Classes imported from Google Classroom show a link back to it.
- **Google Classroom:** "Connect Google Classroom" on Classes links the teacher's Google account with read-only Classroom access (it may be a different Google account from the one they sign in with). They then pick courses to import as classes, with their students; "Sync roster" on a linked class adds students who joined since (nobody is removed). Imported students have no student number or sex until they sign in with Google using the same email: their roster entry becomes theirs, and the join form asks for both. Email-and-password accounts never take over an imported entry, since their email isn't verified. Classroom has no schedule, so add one to each imported class for attendance.
- **Quizzes.** A quiz is reusable content: parts of questions, a test-paper layout and shuffling. A quiz with no session shows as Draft. A Subject dropdown decides the question types offered: General (multiple choice, blank, matching, enumeration, categorization, re-ordering, hotspot), English (+ true/false, essay; no hotspot), Mathematics (+ numeric; re-ordering), Science (all of General + true/false, numeric, essay), and Programming / IT (+ code, SQL query, categorization, re-ordering). "Show all question types" lifts the limit. Questions come from the editor, the question bank, or an Excel import.
- **Quiz editor.** "New quiz" (list, dashboard, class page, or `/teacher/assessments/new`) opens a dialog for the title, subject, description and the names of the parts before the editor opens; "Edit details" reopens it. The editor has a header (breadcrumb, totals, Saved / Unsaved changes), a details card, and one section per part with a labelled divider between parts and "Part settings" (instructions, shuffle, pool). Questions are compact cards that open to edit (Expand all / Collapse all) with a labelled field per setting. A **Cards | Table** switch shows the same quiz as a spreadsheet: a row per question grouped by part, inline editing from the keyboard (Enter or typing edits, Esc cancels, Tab and arrows move, Enter commits and moves down), multi-row bulk edits (points, game points, part), pasting columns from Excel or Sheets, row reorder and a side dialog with the full editor for complex questions. A collapsible contents panel (a drawer on small screens) jumps to the details, any part or any question and marks questions that need attention.
- **Question bank** (`/teacher/question-bank`). Your reusable questions, the ones other teachers shared with you and the school library, with counts (questions, subjects, topics, shared with me). Search, and filter by subject, topic, question type and source (All, Mine, Shared with me, Library); the view and filters are kept in the URL (`?view=topic&subject=…`), so a reload or a link shows the same thing. **By Section** groups the questions by type in test-paper order (count, total points, collapsible); **By Topic** is a subject → topic tree with an "Untagged" group and a side panel (a drawer on small screens) to jump to a subject or topic. A card shows type, subject and topic chips, points and who it is from, and opens to the full prompt and answer key. Tag a question with a subject (free text, optional subject type) and a topic: **Retag** one or many at once, **Manage tags** to rename a subject or topic or merge it into another everywhere. **Share** by subject, by topic or the picked questions with teachers by email (subject and topic shares are live, so questions added later are shared too); remove a share in the same dialog. Shared questions are read-only for the recipient, who can use them in quizzes or **Copy to my bank**. Select questions to retag, share, delete or **Add to quiz** (appended to a draft quiz). **New question** and **Edit** use the same editor as the quiz editor. In the quiz editor, "From question bank" lists your own, shared and library questions with subject, topic and source filters. Subject and topic fields suggest the tags you already use.
- **Markdown.** Prompts, choices, matching items, part instructions, the quiz description, students' essay answers and teacher feedback are markdown (bold, lists, tables, links, code), sanitised, with math written in LaTeX between `$…$` (or `$$…$$`). Every text box has a small toolbar and a Preview tab.
- **Question types.**
  - **Multiple choice:** one correct choice, or several (students tick every correct one), all-or-nothing or partial credit.
  - **Blank:** `fill` ("Identification / Fill in the blank") or `cloze` (a passage with many blanks). A `fill` question with no blanks in the prompt gives students one answer box and lists the accepted answers; with blanks inside the sentence they answer them in place. Blanks are written `{{answer|alternative}}` in the prompt, with an "Insert blank" button. Cloze blanks are typed, picked from a dropdown (options listed in the editor) or taken from a shared word bank with extra distractor words. Case sensitivity is per question.
  - **Matching:** left items, right items and extra distractors on the right; students drag each right item to its left item (keyboard and touch work too).
  - **Categorization:** 2 to 6 named categories (with an optional markdown description) and items with text and/or a picture; students drag each item into its category. An item with no category is a distractor that stays unsorted. Points are shared by the items (equal, or custom weights) with partial credit or all-or-nothing.
  - **Re-ordering:** 3 to 10 items you list in the correct order; students get them shuffled and drag them into order. One share of the points per correct position, or all-or-nothing.
  - **Hotspot:** an image with correct areas (rectangles or ellipses, optionally labelled); students click the image to place up to a set number of markers. One share of the points per area hit, or all-or-nothing (every area hit and no click outside). A tolerance widens every area a little.
  - **True/false, enumeration, numeric, essay (rubric rows with points), code and SQL.**
  - **Drawing:** students draw on a canvas (pen, highlighter, eraser, colours, thicknesses, text labels, undo/redo, pressure on tablets) and/or upload or take up to three photos of work done on paper; the teacher chooses which are allowed (and "Camera only" to refuse gallery picks), an optional background image to draw on, the canvas size, a rubric and the points. Graded by hand like an essay.
- **Parts.** You create, rename, reorder and delete parts, each with markdown instructions, and move questions between them (drag, or "Move to part" and up/down on a phone). A part can shuffle its questions or draw N of its M questions for each student (a pool). The printed paper uses your parts, with points per part ("Part II – Matching (10 pts)").
- **Points.** Every question has points (whole or half, default 1) and, per question, "all or nothing" or "partial credit". Points are shared equally among a question's blanks, pairs, items or tests, or you can set a weight for each. Essay rubric rows carry points that add up to the question's points. Each part and the whole quiz show live totals; bulk-set the points of a whole part or of one question type; every question in a pool needs the same points. A game-points setting (Standard, Double, None) is stored for the game mode and only shown under Advanced. Automatic scores are stored as a fraction and manual scores in points, so changing a question's points recalculates everyone's score.
- **Images.** Add pictures to prompts, part instructions and the quiz description ("Insert image", drag and drop, or paste a file), to multiple-choice options (shown as a grid) and to matching items. PNG, JPEG, WebP or GIF up to 5 MB; the browser shrinks them to 2000 px on the longest side and strips EXIF (location) before uploading. Alt text is required before a quiz can be saved and shows on the printed paper if an image can't load. Duplicating a quiz reuses the same images. Images sit in a private S3 bucket and are shown through short-lived signed URLs, so students can't see question images before the session opens.
- **Randomizing.** Shuffling is seeded from each attempt, so a student's paper is the same after a reload and the teacher sees exactly what they saw. The quiz can shuffle the order of parts, the questions within parts, multiple-choice choices, the matching right column and the cloze dropdowns and word bank; pools draw N questions per student. The answer key and scoring are never affected by the order.
- **Sessions.** "Start a session" on a quiz is one form in numbered sections: the type (Quiz, Exam, Mastery or Game, as cards), who (an **optional class** and its students, plus an optional room password), when (**Start now** or **Schedule for later**, optional close time, time limit, late-join cutoff), attempts (chips: 1, 2, 3, unlimited or custom) and when students see results (chips), the mode's own settings, and anti-cheating (toggle cards with a small drawing of each rule). Every session gets a **7-character join key**, made by the API (no 0/O, 1/I/L; unique among sessions that haven't ended). With a class, the roster is the class's members (`session_students` is the snapshot: filled from the class when the session is created, and when a student joins the class or enters the key as a member); a student who isn't a member can't join, and one who leaves the class or is removed comes off the sessions they haven't started. Without a class there is no roster: any student who has joined a class (so teachers can identify them) and enters the key joins, and "Count in the class record" is hidden. Every session has a **lobby**, like a game: "Start now" opens it at once and a scheduled one opens it at its opening time (or when you press **Open lobby**); students who open the session wait there ("You're in! Waiting for your teacher to start…") and the live view lists who has arrived (`session_students.joined_at`, the invite link and a count), until you press **Start** on the live view, the session page or the sessions list. It then runs and ends at its close time, when you press End, or when time is up; attempts still in progress are then submitted automatically by the API. Each session has its own results page: scores per student, by part and by question.
- **Mastery mode.** Choose "Mastery" when you start a session for self-paced practice: students get one question at a time and see right or wrong at once. A wrong answer goes back into their queue (after about three other questions, or at the end when fewer are left) until it is answered correctly or the **tries per question** (default 3, up to 10) run out. Optional **target score** (%) and **show the correct answer after the last wrong try**. Each question can have a markdown **explanation** (editor, under the question): students read it after a right answer, or after the last wrong try when the correct answer is shown, and it shows with the results. Essays, drawings and code without the runner are accepted once and wait for you to grade them. The queue is stored on the attempt, so a reload (or another browser) carries on exactly where the student was. The session results page has a mastery table (tries per question for each student), the live view shows questions mastered, and the student's results show tries per question and whether the target was reached. Anti-cheating defaults to blocking copy only; mastery mode doesn't use full screen.
- **Game mode.** Choose "Game" for a live game with points. **Teacher-paced** (like Kahoot): open the lobby from the presenter screen (`.../sessions/<session>/present`, built for a projector), students join with the 7-character join key (or the `/join?code=...` link), you start the game and move through each question: the question closes when its timer ends (answering early locks the answer in but shows nothing until then), then the class sees how the answers split, the leaderboard (optional) and, at the end, the podium. While it runs you can **pause** the clock, **change the seconds per question** (an open question keeps its start and gets the new length) and **open any question not played yet** instead of the next one. Players get the game on the whole screen with a full-screen button. You can remove a player in the lobby: the roster row stays, marked removed (`session_students.removed_at`), so they can't join again with the key ("You were removed from this session."). **Student-paced** (like Wayground): each student plays alone with a per-question timer while the presenter screen and the players show a live leaderboard. Settings: time per question (default 20 s), leaderboard after each question, streak bonus. **Points:** a correct answer earns `base × (1 − elapsed ÷ limit ÷ 2)` where the base is the question's game points (Standard 1000, Double 2000, None 0); partly correct answers earn that share and break the streak; each correct answer in a row after the first adds 100 (up to 500); a wrong answer earns 0. Game points are separate from the grading score: the normal score (and so the class record) ignores speed. Essay and drawing questions earn no game points (they keep their grading points): the presenter shows how many answered and a class gallery of the texts and pictures, with names hidden until you show them. Code and SQL questions work in both paces; in a teacher-paced game the room waits up to 30 seconds after the timer ("Checking answers…") for answers still being checked, and an answer that finishes later keeps its score but earns no game points. A Team Relay can't use essays or drawings. The final standings are on the session results page and download as Excel; students see theirs when the game ends. The position of a teacher-paced game is saved in `quiz_sessions` (`game_phase`, `current_question_index`, `question_started_at`), so a restarted API resumes the same question with the time it had left.
- **Team Relay** (a student-paced game played in teams; see `docs/team-relay.md`): players form teams of 2 to 4 in the lobby (they pick a team, or you assign, randomize or balance them). Each member gets their own share of the quiz; a right answer unlocks one piece of the team's secret password (letters, words, numbered letters or your clues), and the team must put the pieces together and submit the password before the round ends. Options: retry a wrong answer for fewer points, let a finished teammate rescue a locked question for part of the points, require every member to confirm a guess, and a solve bonus that shrinks with time. The correct answers stay hidden until the team's debrief, which shows what it missed. Not available for teacher-paced games or quizzes with drawing questions.
- **Game animations:** answers pop in one after another, the last five seconds pulse, the answer bars grow in, points count up, a right answer rains confetti and a wrong one shakes, leaderboard rows slide from their old place to the new one, and the podium rises third, second, first before the crown drops. All of it is CSS and the Web Animations API (keyframes in `globals.css`, helpers in `apps/web/src/features/game/components/game-parts.tsx`), and none of it plays when the device asks for reduced motion.
- **Test paper layout** (a second tab in the editor): school header, paper size, part titles, footer and a live print preview; optional separate answer sheet.
- **Code questions:** Python, Java, C, C++, JavaScript and PHP (optionally with tables and Laravel's DB facade, query builder and Eloquent). Visible and hidden test cases, graded by `apps/runner/` in a sandbox.
- **SQL questions:** students query your tables; their rows are compared with your answer query (column names ignored), with an optional hidden-data check. Graded with sql.js (SQLite) on the server.
- **Review answers:** grade essays, re-score blank and enumeration answers (accept a near-miss), see code and SQL test results, and watch a **typing replay** of code answers.
  Drawing answers show the picture full size with zoom, a replay of the strokes, and tools to draw marks over it; students see the marks on their result.
- **AI help** (OpenAI, Claude or Gemini). **Generate with AI** in each part of the quiz editor drafts multiple choice, true/false, identification, enumeration, numeric and essay questions (with a rubric) from a topic or pasted notes, at a chosen difficulty and points; they land in the part for you to edit and save. The same button on the **question bank** shows the drafts first and adds the ones you tick to your own bank (`bank.add`). On the grading page, **Suggest with AI** drafts a score, feedback and the rubric rows met for an essay answer (or for every ungraded essay in the session), in Standard or **Caveman** style (short, blunt fragments); nothing is graded until you apply it and save, and students never see the drafts. A draft is dropped when the answer changes. Keys: an organization admin saves one key per provider at `/teacher/organization/ai`, used by every teacher of that organization. Keys are stored encrypted (AES-256-GCM, key derived from `BETTER_AUTH_SECRET`, so rotating that secret means re-entering them) and only their last four characters are shown. Default models: `gpt-5-mini`, `claude-sonnet-4-5`, `gemini-2.5-flash`, changeable per key.
- **Anti-cheating** (per session). Rules: full screen with a set number of chances before it submits itself, a log of tab and app switches (Alt+Tab included) with how long each lasted, one screen only (Chrome and Edge), separate switches for right-click, copy, paste (with an exception for code answers), printing and clearing the clipboard at the start, and a watermark with the student's name. Prevention: one question at a time with an optional time per question, a join key, a late-join cutoff, a room password, an IP allowlist (CIDR or plain addresses) and one device per attempt, all enforced by the API along with the timer. Detection: disconnects (heartbeat), time away, out of full screen and offline, device and network changes, a shared-device flag, answers that come too fast, pasted or robot-typed answers with a typing replay for code, SQL, essays and blanks, open dev tools and split screen. The Anti-cheating page gives each student an integrity level (low, medium, high) with the signals behind it, per-type counts and times, a timeline and minutes away, and runs checks after the session: matching rare wrong answers, essay text similarity, timing clusters, and a **similarity check** for code (renamed copies still match; common solutions are ignored). Shared devices or networks are only flagged, since campus Wi-Fi shares addresses. Students never see this.
- **Navigation & review** (session form, quiz and exam): **going back** is Free (any question), Back to marked only (forward, but students may return to a question while it is marked for review) or Forward only; the last two need one question at a time (a paper on one page is always free), and the API enforces them. **Questions a student may mark for review**: None allowed, 1, 3, 5, Unlimited or a custom number. Defaults: free and unlimited; exams start at back-to-marked-only and 5. The live view shows how many questions each student has marked, and the drawer and grading show which.
- **Taking it now:** while a quiz or exam runs, the session's results page shows an aside with the students taking it right now (name, progress, online or not, marked questions), updated live. Students take it on the whole screen, with a full-screen button.
- **Live view** (`/teacher/assessments/<quiz>/sessions/<session>/live`): a table of every student (status, progress, current question, score so far, alerts, minutes away, integrity level) that updates as students answer, with each student's live answers, typing replay and event timeline in a drawer. Controls: start, pause and resume (every deadline moves by the time paused; nobody can save while paused), add time (everyone or one student), end, warn a student, lock and unlock a student (no saving until unlocked), force-submit, and allow back in (frees the attempt from its browser so a student whose computer crashed can continue on another). Every action is stored (`incidents` table) and shown in the timeline. Students see warnings, pauses, locks and new deadlines at once.
- **Exam mode** (the serious mode of a session).
  - **Locked settings:** full screen, tab and app logging, one screen, no right-click, copy, paste or printing, clipboard cleared at the start and the watermark are always on; you can only add stricter rules. Defaults: computers only, auto-submit after 3 chances, late join 15 minutes, one attempt, results released by hand.
  - **Device check and pledge:** phones and tablets are refused when "computers only" is on (checked by the API from the browser's headers). Students read the exam rules and accept an honor pledge (yours or the default) before the first question; the time they accepted is kept.
  - **Device switch approval:** an attempt that is open on another device, or that was away longer than the grace period (default 5 minutes), waits until you approve it. The live view opens each anti-cheating alert as a toast as it arrives (in every session that tracks focus or requires full screen, not only exams), marks that student **Waiting for approval** and has an **Approve device switch** button (also in the student drawer). **Grant retake** in the drawer gives one named student another attempt, with a required reason.
  - **Answer history and grade changes:** every save of every answer is kept. Once results are released, changing a score asks for a reason in a dialog; the old and new score and the reason are kept. Each student's paper has a **paper version** code (like `A7K2-9QX`), shown on their result, in grading and on the report.
  - **Integrity report** per student (`…/sessions/<session>/report/<attempt>`): paper version, pledge time, device and IP, integrity level, counts and minutes per event type, a timeline of events and your actions, every answer version and every grade change. Print or **save as PDF**, or **Export Excel** (sheets Summary, Timeline, Events, Incidents, Answer history, Grade changes).
  - **Results export (Excel)** for every mode, on the session page and the grading page: name, student no., score, max, percent, integrity level, paper version and submission time, then the points of each part and each question.
- **Class record** per class, laid out like the school's Excel class record: categories with weights (ADW 60 + major exam 40), highest possible scores, RS and transmuted grades (TRANSMU table), and the course grade with P/F/FA/DR remarks. Sessions of the class are **added automatically** and score as students submit; removing one keeps it out. Stored in the `class_records` table (categories, items, typed-in scores, absences, DR marks, signatories); linked scores and attendance are filled in when it's shown, and students get only their own scores. Excel download.
- **Attendance:** meetings are worked out from each class's schedule (the days in it, e.g. `MWF`, from the start of the semester to today; `meetingDates` in `packages/domain/src/attendance.ts`), so a new day's meeting appears on its own. Roll calls are stored in the `class_meetings` table; students see only their own. Roll call on a phone (present, late, absent, excused). 7 lates count as 1 absence, and 4 absences flag a drop (the teacher confirms DR). Absences and an Attendance item fill in the class record. Excel download per month with weekday names, plus a semester summary.
- **Collegiate grade sheet** (printable) and the **Summary report on class academic performance** (Reports).

### Students
- Dashboard of what's open, upcoming and done; Schedule; Scores; Classes, where they **join a class with its code** (the first time, also their student number and sex for the grade sheet) or leave one.
- **Join with a key** (dashboard, `/student/join` or `/join?code=...`): enter the 7-character key a teacher shows (any case; spaces and dashes are ignored, so `ABC-DEFG` works). It opens that session: if the session has a class you must be a member of it; a session without a class adds you to it (once you have joined any class) (the late-join cutoff still applies), and it then shows on your dashboard. A game takes you to its lobby (the late-join cutoff still applies), any other session to its lobby, or straight to its page once it is running. In a game you answer on your own screen, see what each answer earned and your rank, and the final standings at the end.
- **Avatar** (`/student/avatar`, or "Customize avatar" in a game's lobby): pick a style (Lorelei, Notionists, Open Peeps, Avataaars, Robots, Pixel art, Thumbs), then each part (hair, eyes, glasses…) and colour, or Shuffle for a new face. Drawn in the browser with [DiceBear](https://www.dicebear.com) (`apps/web/src/features/auth/avatar.ts`); only styles that need no attribution are offered. Everyone has one from the start (drawn from their account); it shows in the lobby, on the leaderboard, on the podium and in the standings, and a saved change shows at once in a game you're in.
- **Standing:** the grade so far in each subject, computed like the class record, with absences used out of the limit.
- Taking a quiz or exam: full screen, a timer the server enforces, answers saved to the server as you type (reloads and other devices pick up where you left off), and **Run** for code (Python and JavaScript in the browser, the rest on the code runner) on the sample tests only.
- **Question overview and review:** every question as a numbered tile (answered, not answered, marked for review, the one you're on, time ran out), in a side panel you can hide on wide screens and a sheet on phones, with "12 answered · 3 marked · 5 left". Click a tile to go there (scrolls on a one-page paper; one question at a time it opens the question when the session's going-back rule allows, and says why when it doesn't). **Mark for review** (flag) on each question is saved on the server. Before submitting, the review screen lists every question with your answer in a few words or "Not answered", marked ones first, with links back; you submit from there. A question you went back to while marked can be unmarked, but once you leave it unmarked you can't return; a question whose time ran out never reopens.
- **Drawing and photo answers:** draw on a canvas (strokes are saved as you go, and the picture is uploaded when you submit and every 30 seconds while you draw), or upload or take photos. Pasting an image is blocked when the session blocks paste.

### Everyone
- **Sign up** at `/register` with Google or any email and start right away. A teacher gets an organization of their own to start with (rename it, invite colleagues with a code, or join another with one); a student joins the organization of the first class they join with a class code. Students give their student number the first time they join a class.
- **Organizations** (`/organizations`, and the switcher in the sidebar): the ones you belong to, with your roles there; pick the one to work in, make a new one (you become its owner), join one with an **invite code**, or join a class with its code. Owners and admins manage theirs at `/teacher/organization`: name, members (add an existing account by email, give a member several roles, remove), invite codes (which roles they grant, for how many days), custom roles (a permission matrix per role, when the server has `ORG_CUSTOM_ROLES=true`), AI keys, and deleting the organization with everything in it (owners only). Class and game join codes are unique across organizations, so a code also says which organization it belongs to; a student who joins a class is made a student of its organization, and the session switches to it. A guest plays in the organization of the game they joined. `/register` opens even when signed in (every "Start free" button leads there); signing up switches to the new account.
- **Join as a guest** (`/join`, or the invite link `/join?id=ABC-DEFG` the game lobby shows): anyone with the key of a game whose teacher turned on **Allow guests** (games without a class only) plays with just a name, no account. The server makes an anonymous account with the `guest` role (Better Auth's anonymous plugin) and a roster entry named as typed, so the teacher sees them like any player; guests play at `/play/<session>` and see the final standings there, and customize their avatar from the lobby like students. Guests can't open anything else; a signed-in student who opens `/join` is sent to their own join page, which also takes `?id=`.
- **Rate limits:** 10 wrong passwords per account in 15 minutes, 200 failed sign-ins per IP in 10 minutes, 100 sign-ups per IP an hour, 300 Google sign-in starts per IP in 10 minutes, 10 wrong class codes per student in 10 minutes, 60 guest joins per IP in 10 minutes, and per teacher 30 AI question drafts and 400 AI score suggestions an hour. The page says how long to wait.
- **Auto sign-out** (`apps/web/src/features/auth/components/session-watch.tsx`): after 30 minutes without activity in any tab, with a "Still there?" warning a minute before (not while taking an exam). Open pages also go to sign-in when the session ends elsewhere (expired, signed out in another tab, suspended). The login page says why and returns them to where they were.
- **Appearance:** Light, Dark or System mode and an accent colour (Blue by default, Violet, Emerald, Rose, Amber) from **Appearance** in the sidebar, saved per browser and applied before the page paints (`apps/web/src/lib/theme.ts`; colour tokens in `globals.css`). The sidebar collapses to icons (remembered); on phones the navigation opens in a drawer from the menu button.
- **Landing page** at `/`: one statically generated page with a floating header (Appearance menu, **Enter a room** for `/join`), a hero with drawn product screens, a strip of the question types, feature cards with small sketches of each screen, an analytics showcase, how it works, pricing from `packages/domain/src/plans.ts`, FAQ and a closing call to action; its parts live in `apps/web/src/components/landing/`. Everything is drawn with the theme's colour tokens, so it follows the visitor's mode and accent. Signed-in visitors get "Open Examinus", looked up in the browser after the page loads. Blocks fade in as they scroll into view, bars fill, and a progress line runs along the top of the window (`components/landing/scroll-effects.tsx`, styles in `globals.css`); none of it plays with reduced motion.

## Run the app
The API runs on [Bun](https://bun.sh) (1.3 or newer) and needs PostgreSQL, Dragonfly (or another Redis-compatible server; `REDIS_URL`) and the variables in `apps/rpc/.env.example` (copy it to `apps/rpc/.env`); the web app needs `apps/web/.env.example` (copy it to `apps/web/.env.local`).
```bash
npm install
npm run db:migrate     # apply migrations
npm run dev:rpc        # http://127.0.0.1:3001 (RPC at /rpc)
npm run plan:set teacher@sic.edu.ph pro 2026-12-31   # change a teacher's plan (free, pro or ai); no date = no end
npm run check:classroom   # Classroom roster sync against a stand-in for Google (needs the test fixture; leaves it as it was)
npm run dev:web        # http://localhost:3000
```

Or with [devenv](https://devenv.sh), which provides Node 22 with npm, Bun, PostgreSQL 18 and Dragonfly:
```bash
devenv shell        # then run the commands above; every variable except the Google pair is set
devenv up           # or start Postgres and Dragonfly, and the API and the web app, in one step (run `npm run db:migrate` yourself)
```

Postgres listens on `127.0.0.1:5434` with an `examinus` database: `postgresql://127.0.0.1:5434/examinus`. Dragonfly listens on `127.0.0.1:6390` (`REDIS_URL=redis://127.0.0.1:6390`).

**From a phone on the same Wi-Fi:** `devenv up` prints `Web app on the network: http://<your-ip>:3000`. devenv finds the machine's address (`DEV_LAN_IP`; set it yourself when there are several interfaces or a VPN), binds the web app, the API and Garage to every interface (`HOST=0.0.0.0`; Postgres and Dragonfly stay on loopback), and sets `PUBLIC_API_URL`, `S3_PUBLIC_ENDPOINT` and `LIVE_ALLOWED_ORIGINS` to that address so live sessions, uploads and sign-in work from there. Google sign-in still needs `localhost:3000` (its redirect URI).

Or with Docker: `docker compose up dragonfly` starts only Dragonfly (on `127.0.0.1:6379`; set `REDIS_URL=redis://127.0.0.1:6379`), and `docker compose up` also builds and starts the API image with `apps/rpc/.env` (see `docker-compose.yml`).

devenv generates `BETTER_AUTH_SECRET` once per machine and stores it in `.devenv/state/auth-secret` (gitignored); delete that file to rotate it, which signs everyone out. Students and teachers can sign up at `/register` with any email, Gmail included, and are signed in right away. Admins create, edit, suspend and remove accounts at `/admin`. Both pages show a Google button; it works once `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set (redirect URI `<BETTER_AUTH_URL>/api/auth/callback/google`). "Sign up with Google" on `/register` creates the account as a teacher (with their own organization) or a student; "Continue with Google" on `/login` only signs in to an existing account with the same email.

Accounts, quizzes, sessions, attempts, grades and the question bank live in Postgres behind the API, and survive restarts. Classes and their rosters are real too. A new database starts empty: create accounts at `/register`, and make the first platform admin in SQL (`update users set role = 'admin' where email = '…'`). A database from before organizations existed gets one default organization (`org-default`, "Examinus") from migration `0019_organizations`, with every account as a member in its old role (admins as owners) and all content in it. Demo data (accounts, classes, quizzes, submissions) exists only as the integration tests' fixture, `apps/rpc/test/fixture/` (`npm run test:fixture -w @examinus/rpc`), which CI loads into its throwaway database.

## Live sessions (WebSocket)
The browser can't send its login cookie to the API's host, so it never logs in to the WebSocket. The web server asks the API for a ticket (`live.ticket`, with the user's cookie): a signed (HMAC with `BETTER_AUTH_SECRET`), 60-second, single-use token for one teacher watching one session or one student following their own attempt. The browser opens `ws(s)://<API>/rpc/live` and sends the ticket with each request; every reconnect (with growing delays) gets a new ticket.
- `PUBLIC_API_URL` in `apps/web/.env.local` (optional): the API as the **browser** reaches it, e.g. `https://api.example.com` (the `ws://` / `wss://` URL is derived). The web server reads it at request time and sends it with each ticket, so changing it needs no rebuild. Without it, `API_URL` is used, which is enough for local development.
- Origin check: the API refuses a WebSocket upgrade from a browser whose `Origin` isn't the web app's: `LIVE_ALLOWED_ORIGINS` (comma separated, in `apps/rpc/.env`), by default the origin of `BETTER_AUTH_URL`. Better Auth trusts the same list (its own origin check on sign-in), so the web app's every address goes there. Requests without an Origin header aren't browsers and still need a valid ticket.
- The API must be reachable over WebSocket from browsers (a reverse proxy needs `Upgrade` headers and a long idle timeout).

## Run S3 storage (images and drawings)
Question images and students' drawings and photos are stored in an S3-compatible bucket (AWS S3, Cloudflare R2, Garage or MinIO). `devenv up` starts [Garage](https://garagehq.deuxfleurs.fr) with its S3 API on `127.0.0.1:3910` (data in `.devenv/state/garage`), creates an `examinus` bucket with a development key and CORS rules, and sets the variables below. Without them the API still starts, but uploads fail with "Image storage isn't set up" and images are not shown.

| Variable | Meaning |
|---|---|
| `S3_BUCKET` | Bucket name, e.g. `examinus` (private) |
| `S3_REGION` | e.g. `us-east-1` (Garage's default region) |
| `S3_ENDPOINT` | Empty for AWS S3; `http://127.0.0.1:3910` for devenv's Garage; the account endpoint for R2 |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Credentials with read, write and delete on the bucket |
| `S3_PUBLIC_ENDPOINT` | Optional: the address browsers use to reach the bucket when it differs from `S3_ENDPOINT` |

Browsers upload straight to the bucket (presigned POST, type and 5 MB limit enforced by S3), so the bucket's CORS rules must allow `POST` and `GET` from the web app's origin. devenv sets them on its Garage bucket; on AWS S3 or R2 add a CORS rule with the web origin, methods `POST` and `GET`, and any header. Without devenv, run any S3-compatible server yourself, create the bucket and a key with read and write on it, set CORS, and fill in the variables.
A daily job in the API deletes uploads that were never confirmed and images that no question, answer or bank entry refers to, once they are more than a day old.

## Desktop app (students)
`apps/desktop/` is **Examinus Desktop**, the student client for exams: a [Tauri 2](https://tauri.app) window (Rust, no front-end framework of its own) that shows the hosted web app and adds what a browser tab can't. The plan is `docs/native-clients-plan.md`; this is phase D1 (the shell) plus version checking.
- **One window, one site.** The webview is pinned to the web app's origin: a link anywhere else (in a question, the release page) opens in the system browser and the window stays put. `target="_blank"` links and `window.open` navigate the window itself so the same rule applies. The web app gets no Tauri APIs (it is a remote origin with no capability); only the shell's own "Connecting…" page, shown while the web app can't be reached, has one command (`retry`).
- **It says what it is.** The user agent ends in `ExaminusDesktop/<version>` (the API reads it from the forwarded headers: `clientOf` in `packages/domain/src/client.ts`), and a frozen `window.__EXAMINUS_DESKTOP__ = { version, platform }` is set before any page script runs (the exam's device check shows it as "Examinus Desktop").
- **Version checks, two of them.** (1) The API's `DESKTOP_MIN_VERSION` (`apps/rpc/.env`): a desktop build older than it can't open a paper or start an attempt (`attempt.paper` and `attempt.start` fail with `ClientOutdated`), and the student pages show "Update Examinus Desktop" with a link to the releases; raise it after a security fix so every lab machine updates before the next exam. (2) At start-up the shell asks GitHub for the newest `desktop-v*` release (`DESKTOP_RELEASES_REPO`, default this repository) and offers the download page when it is newer. Installs aren't automatic: there is no update signing key yet.
- **Where it points.** `EXAMINUS_WEB_URL` is baked in at build time (the release workflow sets it from the repository variable of the same name) and can be overridden by the same environment variable at run time, which is how development works: `EXAMINUS_WEB_URL=http://localhost:3000 npm run dev:desktop` (needs the [Tauri prerequisites](https://tauri.app/start/prerequisites/): Rust and, on Linux, webkit2gtk 4.1). `npm run build:desktop` makes the installers for the current OS.
- **Exit password.** A session may carry an exit password (Anti-cheating step, "Password to exit the desktop app"; shown to the teacher on the session page like the room password). While a student's attempt is in progress, Examinus Desktop refuses to close (title bar, Alt+F4, Cmd+Q) and the web app shows a dialog instead; the teacher types the password there (`attempt.verifyExitPassword`, wrong tries rate limited per attempt) and the app closes. The web app signals the shell by navigating to `examinus-desktop://lock|unlock|exit`, which the shell swallows (`on_navigation`); browsers ignore the setting.
- **Not yet** (next phases in the plan): the rest of lockdown while an attempt is in progress (D2), process, VM and display checks (D3), build attestation and signed updates (D4), the system check and the "Require desktop app" session setting (D5).

## Versioning and releases
The API and the desktop app follow [Semantic Versioning](https://semver.org) separately, each with its own tag series in this repository's GitHub releases:

| App | Version lives in | Tag | Bump the **major** when | **minor** when | **patch** when |
|---|---|---|---|---|---|
| API (`apps/rpc`) | `apps/rpc/package.json` (published as `auth.config.api.version`) | `rpc-vX.Y.Z` | an RPC, schema or error changes so an existing client breaks (a field removed or renamed, an error no longer returned) | an RPC, field or error is added, or behaviour changes compatibly | a fix with no contract change |
| Desktop (`apps/desktop`) | `apps/desktop/package.json` **and** `src-tauri/Cargo.toml` (must agree; CI checks) | `desktop-vX.Y.Z` | the shell needs a newer API or the bridge changes incompatibly | a new check or capability | a fix |

Release: bump the version in a commit, then `git tag rpc-v1.3.0 && git push origin rpc-v1.3.0` (or `desktop-v…`). A tag that doesn't match the file fails the workflow. A pre-release version (`1.3.0-beta.1`) is published as a GitHub pre-release and the shell's update check ignores it. After a desktop security fix, set `DESKTOP_MIN_VERSION` on the API to the fixed version so older builds are refused.

## API
- `packages/contract`: the RPC groups, their request and response schemas and the tagged errors, shared by the web app and the API. Add a procedure here first. One entry per group (`@examinus/contract/auth`, `admin`, `class`, `enrollment`, `attendance`, `quiz`, `session`, `attempt`, `live`, `game`, `ai`, `asset`, `avatar`, `class-record`, `classroom`), plus `errors` (only the errors every feature can return: `Unauthorized`, `Forbidden`, `NotFound`, `Conflict`, `TooManyRequests`), `middleware` and `api` (`ApiRpcs`, the merge of every group, and the RPC paths). There is no barrel: import from the entry you need.
- `packages/domain`: pure logic and the Effect Schema domain model (no RPC, database or clock), one entry per module (`@examinus/domain/question`, `quiz`, `scoring`, `analytics`, `integrity`, `shuffle`, `relay`, `game`, `ai`, `asset`, `avatar`, `permissions` and so on; see its `exports`). The contract imports the domain, never the other way round.
- Quiz RPC groups (`packages/contract/src/quiz.ts`, `session.ts` and `attempt.ts`): `quiz.*` (quizzes, parts, questions), `session.*` (create, update, start, end, release results, attempts, grade, class scores) and `attempt.*` (my sessions, the seeded paper, start, autosave, run sample tests, submit, integrity events, result, scores). Scoring and seeded shuffling are shared pure code in the domain (`packages/domain/src/scoring.ts`, `shuffle.ts`).
- Question bank RPC group (`packages/contract/src/bank.ts`): `bank.*`. `list` returns the shared demo library, the teacher's own questions and those shared with them as `BankQuestion` (`question`, `subject`, `subjectArea`, `topic`, `owner`, `mine`, `sharedBy`); `add`, `update`, `delete`, `retag` (many questions at once) and `renameTag` (rename or merge a subject or topic across all of the teacher's questions) change only the teacher's own questions; `share` (by subject, by topic, or by picked questions, to teachers by email), `shares` (what I share and what is shared with me), `unshare`, and `copy` (a visible question into my bank with new ids). Questions are addressed by `question.id`. Anything the caller doesn't own (for writes) or can't see (for reads) is `NotFound`; an email that isn't a teacher account is `UnknownRecipients` (nothing is shared). Subject and topic shares are live: questions added to them later are visible to the recipient too. Shared questions are read-only, and their images are visible to the recipient. `Question.topic` and the bank's topic column always agree. Permissions: `questionBank` read, create, update, delete, share (teachers).
- Asset RPC group (`packages/contract/src/asset.ts`): `asset.createUpload` (presigned POST for one image, `question` images for teachers and `answer` images for students), `asset.confirm` (checks the file really is that image, records size and dimensions) and `asset.urls` (signed GET URLs only for assets the caller may see: their own, a quiz's images for its owner or for students on an open or ended session, students' answer images for the student and the session's teacher).
- AI RPC group (`packages/contract/src/ai.ts`): `ai.status`, `ai.generate` and `ai.suggestGrade` (`ai:use`, teachers), `ai.keys`, `ai.setKey` and `ai.removeKey` (`ai:configure`, organization owners and admins). The organization's keys live in `ai_keys` (one per provider and organization), suggestions in `answers.ai_suggestion`; provider calls are in `apps/rpc/src/features/ai/`.
- Organization RPC group (`packages/contract/src/organization.ts`): `org.create`, `org.setActive` (the session's active organization; `auth.session` returns the user's `organization` with the permissions their roles grant there, and their `memberships`), `org.update`, `org.delete`, `org.members`, `org.addMember`, `org.setMemberRoles`, `org.removeMember`, `org.invites`, `org.createInvite`, `org.revokeInvite`, `org.joinWithCode`, and `org.roles`, `org.createRole`, `org.updateRole`, `org.deleteRole` (custom roles, `ORG_CUSTOM_ROLES`). Tables: `organizations`, `members` (`role` is comma-separated), `organization_invites`, `organization_roles`, and `organization_id` on `classes`, `quizzes`, `bank_questions` (null with `owner_id` null: the shared demo library), `bank_shares`, `assets`, `ai_keys` and `students` (one roster entry per account and organization; student numbers are unique per organization). Every ownership check in the API filters by the active organization, so a record from another organization is `NotFound`.
- Avatar RPC group (`packages/contract/src/avatar.ts`): `avatar.mine` and `avatar.save` (`avatar:update`, students and guests). The choices (style, seed, parts, colours) live in `users.avatar`; without one, the API sends the default style drawn from a hash of the user id. `GameRow`, the lobby, `GameMe` and `GameStanding` carry each player's avatar.
- Session lifecycle: a session is `scheduled` until its opening time (or `session.openLobby`), then in its `lobby` until the teacher's `session.start` (refused from `scheduled`: every session goes through its lobby; games start from their presenter), `running`, then `ended` at its closing time or when the teacher ends it. `sessionStatus` derives the status on every read (an opening time that has passed means `lobby`, never `running`). `attempt.paper` in the lobby returns the session with no paper and records the student's arrival; `attempt.start` waits for `running`. A background job in the API runs every 30 seconds to open lobbies, end sessions and to submit attempts that ran past their time limit or the session's close (plus a 60-second grace). Answers are graded on submit: automatic scores in the API, code through the code runner (`RUNNER_URL`, `RUNNER_SECRET`), SQL through sql.js.
- Live sessions: `session.pause`, `resume`, `addTime`, `warn`, `setLocked`, `forceSubmit`, `allowBackIn` and `liveAttempt` (teacher actions), `live.ticket`, and the WebSocket group `LiveRpcs` (`packages/contract/src/live.ts`) at `/rpc/live` with the streams `live.teacher` (a snapshot, then changes; each row carries `joinedAt`), `live.student` (pause, lock, deadline, warnings, "submitted") and `live.lobby` (ticket target `lobby`: the session, again on every change, for a student waiting in the lobby). The state is in Postgres (`quiz_sessions.paused_at`, `attempts.extra_ms` and `locked`, `incidents`), so a restarted API or a reconnecting browser shows the same thing; the changes in flight travel over Dragonfly channels (`platform/LiveBus.ts`, `features/live/Service.ts`, `LiveHub`), and redeemed tickets are remembered there.
- Mastery mode: `attempt.masteryState` (the saved queue and the question to answer now) and `attempt.masteryAnswer` (grades one try with the contract scoring and returns the feedback and the next state). The queue is `attempts.mastery_queue`, tries are `answers.tries` with every try in `answers.tries_log`, and the settings are `quiz_sessions.mastery`. The logic is in `apps/rpc/src/modes/mastery.ts`; `attempt.paper` sends no questions in this mode and `attempt.saveAnswer` is refused.
- Navigation and marks: `quiz_sessions.navigation` (`free`, `marked_only`, `forward_only`) and `max_marked` (0 off, null unlimited); `attempts.question_index` and `furthest_index`; `answers.marked_for_review` (a marked question without an answer has a row with a null value) and `answers.shown_ms` (time used on earlier visits of a question with a time limit). `attempt.goTo` moves one question at a time as `moveRefusal` in `packages/domain/src/review.ts` allows, `attempt.setMarked` refuses past `max_marked` (and, one question at a time, marking anything but the question you're on), and `attempt.saveAnswer` only takes the question the student is on. `attempt.paper` sends `review` (each question's answered/marked/closed state and answer summary) and `progress.furthest`.
- Game mode: `game.find` (join key to session; adds the student to a classless session), `game.join`, `game.answer`, `game.next` (student-paced), the teacher's `game.openLobby`, `start`, `advance`, `end`, `kick`, `standings` and `gallery`, and the WebSocket stream `live.game` (ticket target `game`) that sends each screen its whole `GameView` (presenter or player; a player never receives other players' answers or the answer before the question closes). The engine is `apps/rpc/src/modes/game.ts`: an in-memory room per game rebuilt from `quiz_sessions` (`game_phase`, `current_question_index`, `question_started_at`, game settings), `attempts` (`points`, `game_streak`) and `answers` (`game_points_earned`, `time_ms`) after a restart; a 500 ms ticker closes questions whose time is up. Points are `gameAnswerPoints` in `packages/contract/src/game.ts`. Answers only go through `game.answer`: `attempt.paper`, `start`, `saveAnswer`, `runSampleTests`, `goTo` and `submit` refuse a game with the Conflict `gameAttemptMessage` (the web app opens the game screen on it), and the live answer replaces any stored row for its question.
- Exam mode: `quiz_sessions.exam` (computers only, honor pledge, device grace minutes), `attempts.pledge_accepted_at`, and the tables `answer_history` (every save) and `grade_changes` (score changes after release, with the reason). `session.create` and `session.update` refuse an exam with a locked anti-cheat setting off (`examLockedSettings` in `packages/domain/src/exam.ts`); `attempt.start` refuses phones and tablets (user agent and client hints) when computers only is on and refuses a new attempt without `pledgeAccepted`; an attempt on another device, or away longer than the grace period, gets `DeviceApprovalRequired` until the teacher calls `session.allowBackIn` (recorded as the incident `device_switch_allowed`). `session.grantRetake` (incident `retake_granted`, which adds one attempt for that student), `session.examRecord` (the integrity report's data) and the optional `reason` of `session.grade`. The server rules are in `apps/rpc/src/modes/exam.ts`.
- `apps/rpc/src`: `platform/` (shared infrastructure: `AppConfig`, `Database`, `Cache`, `LiveBus`, `RateLimiter`, `Storage`, `Runner`, the SQL grader, and `Observability` with `RpcCallLog` for logging and tracing), `features/` (`auth` with `BetterAuth` and the auth middleware `Session.ts`; `quiz`, `session`, `attempt` and `live` with a `Repo.ts` for the database, a `Service.ts` for the rules and pure `rules.ts`/`mappers.ts`), Effect services still at the root (`Assets`, `Ai`), RPC handlers (`handlers/`) and the server (`main.ts`). It runs on Node's built-in TypeScript support; no build step.
- `apps/web/src/lib/api/client.ts`: the RPC client. Server code calls `callApi((api) => api["admin.listUsers"](), forwardedHeaders(...))`.

Container: `apps/rpc/Dockerfile` (build from the repo root with `docker build -f apps/rpc/Dockerfile .`). It listens on `0.0.0.0:$PORT` (default 8080) and needs `DATABASE_URL`, `REDIS_URL`, `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` at runtime; it does not run migrations. `docker-compose.yml` runs it next to Dragonfly.
The port opens before the routes are ready and answers 404 until then (for about 10 seconds on a cold start), so a host must wait for `GET /health` to return 200 before sending traffic. On Cloud Run, use an HTTP startup probe on `/health`, not the default TCP probe.

## Code structure
The API is moving to one folder per feature (see issue #93). The target shape:

```text
packages/
  domain/      @examinus/domain: pure logic and Schemas (question and quiz model, scoring, analytics, integrity, permissions), one entry per module, no RPC
  contract/    @examinus/contract: RPC groups, request/response schemas and tagged errors only, one entry per group (auth, class, quiz, session, attempt, game...), plus errors, middleware and api
apps/rpc/src/
  features/<feature>/
    Repo.ts      database access only, as an Effect service (no Drizzle elsewhere)
    Service.ts   business rules (Context.Service + Effect.fn)
    Handlers.ts  thin: permission, then service, then error mapping
    Jobs.ts      background work: Layer.effectDiscard + Effect.repeat(Schedule...) + forkScoped
    index.ts     exports one `Live` layer (Layer.mergeAll)
  platform/    AppConfig, Database, Cache, RateLimiter, Storage, Observability (logging and tracing)
  main.ts      merges feature layers only
```

`platform/`, `packages/domain` and the thin `packages/contract` exist today. The feature folders arrive in the later phases of the issue.

Rules that already apply:
- Read environment values only in `platform/AppConfig.ts`; services take them from the `AppConfig` service. (The scripts in `src/database` run without the server layers and read their own.)
- Name every service method and handler `Effect.fn("<Feature>.<method>")`; handlers use their RPC name (`"avatar.save"`). The span then shows up in traces.
- `packages/domain` holds rules that need no RPC, database or clock; `packages/contract` holds what crosses the wire and imports the domain. Neither imports from `apps/*`.
- Each package lists its entry points in `exports` (one per module or RPC group); there is no barrel. Import `@examinus/domain/<module>` or `@examinus/contract/<group>`, and add a line to `exports` for a new file. `npm test` (`bun test packages apps/rpc/src`) runs the domain tests and the API's service tests.
- Service tests sit next to the code (`features/<feature>/*.test.ts`, run by Bun): they build the service with `Layer.succeed(XRepo, stub<XRepo["Service"]>("XRepo", { ...only the methods used }))` for its Repo and other services plus `testConfig` (`apps/rpc/src/testing/config.ts`), and check rules and typed refusals through the public methods. `apps/rpc/test/` holds the integration tests, which need the running API and a migrated database with their fixture loaded (`npm run test:fixture -w @examinus/rpc`).

Checklist for a new feature:
1. Add the RPC group, its schemas and its own tagged errors (anything beyond the shared ones in `errors.ts`) to `packages/contract` (one entry file for the group; the web app branches on `_tag`, never on message text) and register it in `ApiRpcs`.
2. Put pure rules (scoring, validation, formatting) in `packages/domain`.
3. Create `apps/rpc/src/features/<feature>/` with `Repo.ts` (all queries), `Service.ts` (rules, `Effect.fn` methods), `Handlers.ts` (permission, service call, error mapping) and `Jobs.ts` if it needs background work.
4. Read any new setting through `AppConfig`, not `Config` or `process.env`.
5. Export one `Live` layer from `index.ts` and add it to `main.ts`.
6. Add tests (service tests with test layers, plus an integration test if it touches the database) and update this README.

### Web app (`apps/web/src`)
```text
app/                 Next.js App Router routes (served by vinext) only: page.tsx, layout.tsx, loading.tsx, route.ts. Thin: read data through the feature, render its components
features/<feature>/  auth, admin, classes, attendance, records, quiz, session, attempt, live, game, mastery, exam, ai, assets
  data.ts            server-side reads and writes over RPC (data/*.ts when big); callApi lives in lib/api
  actions.ts         the feature's 'use server' actions
  components/        its client and server components
  *.ts               its own helpers (attempts, grading, quiz-editor, integrity, ...)
components/          shared UI only (ui, dialog, menu, markdown, code-editor, app-shell, nav, landing, legal) and question-kinds/ (editor, input, review and print per question type)
lib/                 shared infrastructure: api/ (the RPC client, the one server-side ManagedRuntime, and read/write helpers), auth/dal.ts, format, theme, validate...
```

### Adding a question type
Everything that differs between question types lives in one place per type: its kind, `packages/domain/src/kinds/<type>.ts`, a `QuestionKind` (see `kinds/base.ts`): its schemas (teacher question, stored body, student question), the student's view (`toStudent`), scoring (`autoScore`, `units`, `partResults`, `reviewable`), answer and key text, the review summary, images, shuffling, answer cleaning, and the optional capabilities only some types have (AI drafts, game tallies and rules, similarity checks, a code or SQL checker). The registry `kinds/index.ts` maps each type to its kind and is typed on `QuestionType`, so a type without a kind does not compile. The scoring, answer-text, review, asset, shuffle, analytics, integrity and game modules, and the API (answer cleaning, game tally, AI drafts, code and SQL checks), only look the kind up; they never switch on the type.

1. Write `kinds/<type>.ts`: the schemas and the `QuestionKind` object. Leave out optional members the type doesn't have; don't add stubs.
2. Add the type to `questionTypes` and the three unions (`Question`, `QuestionBody`, `StudentQuestion`) in `question.ts`, and to the registry in `kinds/index.ts`.
3. Add the `exports` line for the new module in `packages/domain/package.json` and the type to the database enum (a migration: `npm run db:generate`).
4. The web app's module for the type (editor, answer input, review, print) is `apps/web/src/components/question-kinds/<type>/`, registered in `components/question-kinds/registry.ts`.

## Cache (Dragonfly)
The API keeps no state of its own between requests except the game rooms. Everything else short-lived is in [Dragonfly](https://www.dragonflydb.io) through Bun's built-in Redis client (`apps/rpc/src/platform/Cache.ts`, keys prefixed `examinus:`):

| What | Keys / channels |
|---|---|
| Rate-limit counts (API limits, code runs, Better Auth's own limits) | `rate:*`, `auth-rate:*` (sliding windows) |
| Redeemed live tickets (single use) | `ticket:<jti>`, until the ticket would expire |
| Teacher-panel heartbeat throttle | `seen:<attemptId>` (10 s) |
| Quiz details for live sessions | `quiz-detail:*` (30 s) |
| SQL sample results | `sql-sample:<hash>` (24 h) |
| Game question extras (signed image URLs, SQL sample) | `game-extras:*` (5 min) |
| Players connected to a game | `game:<sessionId>:online` (one entry per screen, refreshed every 10 s) |
| Live and game event buses | channels `live:<sessionId>:teacher`, `live:<sessionId>:student`, `game:<sessionId>` |

Game rooms (players, scores, clocks, locks) stay in the API process as a working copy of Postgres, rebuilt after a restart, so games still need a single API instance. Dragonfly needs no persistence: losing it only resets counts and caches. Any Redis-compatible server works in its place.

## Database
Schema: `apps/rpc/src/database/schemas/`. Migrations: `apps/rpc/src/database/migrations/`.
```bash
npm run db:generate -- --name <change>   # after editing the schema; commit the generated SQL
npm run db:migrate                       # apply pending migrations to DATABASE_URL
```

Any PostgreSQL 18 works, local or hosted. With [Neon](https://neon.tech): create a project (Postgres 18), copy its
connection string (it ends in `?sslmode=require`; the API's Bun client and drizzle-kit both connect over TLS) and
put it in `DATABASE_URL`, then `npm run db:migrate`. Use the
**direct** (non-pooled) connection string for `db:migrate`; the API itself can use either. In `devenv`, exporting
`DATABASE_URL` before `devenv shell`/`devenv up` makes the API use it instead of the local Postgres (which still
starts). For production, set the same URL as the `DATABASE_URL` secret of the `production` environment so CI
migrates it (see CI below), and on the API's host.

## Observability
Traces, metrics and logs go out over OpenTelemetry (OTLP) from the API, the web app and the runner. Nothing is exported until `OTEL_EXPORTER_OTLP_ENDPOINT` is set.
```bash
docker compose --profile observability up otel-lgtm   # Grafana http://127.0.0.1:3300 (admin / admin)
```
It starts Grafana with Prometheus, Tempo and Loki (`grafana/otel-lgtm`) and takes OTLP on `127.0.0.1:4318` (HTTP) and `4317` (gRPC). Then set these in the environment of the API (`apps/rpc/.env`), the web app and the runner (`apps/runner/.env`):

| Variable | Meaning |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://127.0.0.1:4318`; empty (default) means no export |
| `OTEL_SERVICE_NAME` | Default `examinus-api`, `examinus-web` or `examinus-runner` |
| `OTEL_RESOURCE_ATTRIBUTES` | e.g. `deployment.environment=dev`, shown as the dashboards' Environment filter |
| `OTEL_EXPORTER_OTLP_HEADERS` | `key=value,...`, for a hosted backend that needs authentication |
| `OTEL_TRACES_SAMPLER_ARG` | Share of traces kept, 0 to 1 (default 1) |

`devenv up` starts the same Grafana (process `grafana`, in Docker; Docker must be running) and points the API and the web app at it (`OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318`, `deployment.environment=dev`), so nothing needs setting there. Open http://127.0.0.1:3300 (admin / admin). Stop the compose `otel-lgtm` first if it's running: both use the same ports.

The folder "Examinus" holds four dashboards: API overview (requests, errors, latency, database, cache, rate limits, process), Exams and live (streams, game rooms, attempts, integrity events), Runner and AI (job durations and outcomes, AI calls and failures) and Traces and logs (slow and defective traces, API errors). Five alert rules (API defects, p95 over 1 s, `attempt.saveAnswer` errors over 2%, runner unreachable, event-loop lag over 200 ms) load with them. No contact point is provisioned, so they only show in Grafana's Alerting page until you add one. The files are in `observability/grafana/`.

Metrics and span attributes carry no user, exam, attempt or question ids, no emails, no answers and no SQL parameters: only RPC names, outcomes, types and counts. Log lines are exported as the API writes them, and a few warnings name a question or session id. When the API itself runs in Docker (`docker compose --profile observability up`), its endpoint is `http://otel-lgtm:4318`.

## CI
`.github/workflows/ci.yml` runs on pull requests and pushes to `main`: lint, typecheck, the unit and service tests (`npm test`: the domain's, and each API feature's service with test layers, no database), migration checks against a fresh PostgreSQL 18 (migrations apply, and the schema has no ungenerated changes), the integration test fixture, an API start-up check with Dragonfly, the integration tests (`npm run test:integration -w @examinus/rpc`: Team Relay, sessions, attempts and the classic game, against the running API), a Google Classroom roster sync check against a stand-in for Google (`npm run check:classroom`), and the web build.

To migrate production on every push to `main`, add a `production` environment with a `DATABASE_URL` secret and set the repository variable `MIGRATE_ON_DEPLOY` to `true`.

`.github/workflows/desktop.yml` compiles the desktop shell (`cargo fmt`, `clippy`) when `apps/desktop` changes, and builds and publishes the installers on a `desktop-v*` tag. `.github/workflows/release-rpc.yml` creates the API's release on an `rpc-v*` tag. See "Versioning and releases".
